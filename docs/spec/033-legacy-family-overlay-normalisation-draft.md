# 033 — 舊家族的 overlay 位址正規化

狀態：**READY**（2026-09-26 兩輪獨立審查後）
日期：2026-09-26
前置：規格 032、[phase-264](../re/phase-264-overlay-units-and-text-glyphs.md)、
[phase-266](../re/phase-266-station-screens-survey.md)。

## 1. 問題

規格 200 系列的舊家族（主選單、名冊、角色頁、技能頁、身體圖示、加入後選單、技能離開等）
在角色建立流程中量得呼叫端，events 檔寫成 `37F1:1856`、`2368:0945` 這類絕對段位址。
遊戲進行後同一段程式載到別的段（phase-266：Hq 的隊伍管理選單在 216E、角色頁在 24AA），
這些家族就對不到，畫面維持英文。更糟的是，角色建立期的 1C41 放 unit `1799A`，
Salvation III 的 1C41 卻放 `27BBE`：照字面比對可能把別的 unit 的程式當成登記過的位址。

## 2. 契約

### 2.1 正規化

- 以規格 032 的 stub 解析，定義段的正規化 N(S)：
  1. S 恰為一個已知 unit 的目前 LoadSeg，且該 unit 在規格 032 §3.4 的換算表中有
     角色建立期段 L → N(S) = L。
  2. S 恰為一個已知 unit 的目前 LoadSeg，但該 unit 不在換算表 → N(S) = 0xFFFF
     （任何舊家族位址都不會用到此段）。
  3. S 同時是兩個以上 unit 的 LoadSeg → 0xFFFF。
  4. S 不是任何 unit 的 LoadSeg（主程式段等）→ N(S) = S。
- 一個位址的正規化是 (N(S), 偏移)。
- 在角色建立期（unit 都在換算表所列的段），N 是恆等映射，舊家族行為與收據不變。
- 實作用新函式計算 N，不能直接借用規格 032 `OverlayUnits.Key()` 的回傳值：`Key()` 對
  「沒有 unit」與「兩個以上 unit」都退回原始段，分不出情形 3 與 4；N 需要命中數。

### 2.2 套用點

只在四個讀取段位址的入口套用，下游的舊家族程式不改：

1. `live_menu.go` 每步的 `CS:IP`（menu recorder 的 at）；
2. `live_menu.go` dispatcher 進入時從堆疊讀的呼叫端；
3. `live_runtime.go` `BeforeStep` 交給舊家族（技能離開、加入後選單、動作列、手冊、劇情頁、
   身體圖示）的 `at`；
4. `live_runtime.go` 劇情頁從堆疊讀的呼叫端。

規格 027–030 的通用家族繼續用原始位址與規格 032 的解析，不經過 N。

N 只套用在「交給舊家族」的那一份位址複本，不就地覆寫共用的 `at`／`caller` 變數。
同一個變數還要和主程式段的固定位址比較（`0763:026B` 字形進入、`0CF4:1B3A` 清除、
`0763:0424` dispatcher、劇情頁的 `0763:04FF` 等），並交給通用家族自行解析；這些比較
不經過 N。

### 2.3 更新時機與成本

- N 以 65,536 格的陣列查表（只在交給舊家族時查，最多每步一次陣列存取），陣列在下列時點依目前 LoadSeg 重建：
  每次回掃、每次 `0763:0424` 與 `0763:056C` 進入、執行不連續之後。
- 重建之間 unit 若換段，查表可能過時。影響：舊家族對不到（顯示英文），或把別的 unit
  當成登記段；後者還須字串雜湊也相同才會畫，舊家族一律以整串雜湊認領，實務上不會誤畫。
  dispatcher 進入時會重建，所以呼叫端的判定是準確的。

## 3. 不做什麼

- 不改舊家族的 events 檔與比對邏輯；不改 overlay 管理器。
- 不涵蓋 receipt 工具的舊家族 oracle 路徑（`watcher.go` 的 Install），只涵蓋 live runtime。

## 4. 驗收

1. 單元測試：N 的四種情形、陣列重建、角色建立期恆等。
2. 七條專屬家族回歸（`phase254-live-families-parity`）與上一輪相同。
3. Salvation III：Hq 隊伍管理選單與角色頁由舊家族畫出中文（`abm2.sh` 延伸路徑）。
