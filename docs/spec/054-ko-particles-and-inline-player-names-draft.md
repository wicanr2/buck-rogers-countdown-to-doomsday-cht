## 1. 為什麼要做

1. **助詞**：韓文的主格、受格、與格助詞隨前一詞的尾音不同（`은／는`、`이／가`、`을／를`、`와／과`、`으로／로`）。譯文為執行期才知道前詞的情形留了括號並列形標記（`은(는)`、`이(가)`、`을(를)`、`와(과)`、`(으)로`，規格 043 §3 約 220 列）。
   前詞若是韓文（怪物名、物品名、玩家名音譯），尾音其實可以決定，標記就可以換成正確的助詞。
2. **句中玩家名**：戰鬥與探索的訊息句裡，隊員名目前保持原版英文（`FLAVIUS은(는) 자신의 전술 판정을 한다.`；ja `FLAVIUSは自分の戦術判定を行う。`），而同一個畫面的右欄與 ECL 敘事裡同一個人是音譯（`플라비우스`、`설레스트(CELESTE)`）。

## 2. 證據

來源：證據蒐集（2026-10-02，dosgolem `e992599`，在 Docker 內以 `cp/*.state` 重播並與原 trace 逐列比對 W／D 序列；`workplace/phase317-evidence/`，ignored；
重播 71 批中 66 批逐列相同，不一致者已排除）。語料只有同一支隊伍（六位隊員），回報只列計數與呼叫端，不列原版英文句子。

已證實：

1. 句中隊員名不是「原版畫名字、覆繪畫片段」：型態 B（24 筆）原版以**一次** ECL 印字呼叫（`0763:056C`）印出整句，覆繪層整句重畫，名字是引擎範本把 `_` 槽的原文原樣填入（`engine_text.go` `translateLine` 的 `default` 分支，`monsterSlot` 沒命中時 `zh[i] = p.Text`）；
   這條路徑不經 dispatcher `0424`，沒有 `MemberAt` 可用的字串指標（堆疊上組好的整句）。呼叫端：`OVR:27BBE:0AE5`（18）、`OVR:1CA15:1E42`（5）、`OVR:00904:2813`（1）。
2. 型態 D（6 筆）：dispatcher `0763:1282` 畫整句（`<名字> leads <怪物名>.` 型），已在 `engine-dispatch-callers.tsv` 的 `allow`，但 `NeedsParty` 對它回 false。
3. 型態 A（36 筆）：ECL 敘事把名字當一次獨立 `056C` 呼叫（`OVR:00904:0B79`／`0B4A`），後面 `0B4A` 續印片段；其中 35／37 已被規格 038 §3.3 處理成「音譯(英文)」。片段呼叫的起始欄恰等於名字結尾欄（逐字形 36／36 同列且欄差 1）。
   執行期 ko 輸出的 `설레스트(CELESTE) | 은(는) 서서히 …` 中 `은(는)` 沒有依尾音選擇。
4. 型態 C（3 筆，同一檔）：物品頁標題 `<名字>'s Gear`：dispatcher `235A`（列 1 欄 1）畫名字，現行保留英文；型態 E（1 筆）：名字黏在原版字串尾端沒有呼叫邊界（規格 038 §4 排除）。兩者不在本規格範圍。
5. `NeedsParty`／`readEclPlayerContext` 目前只對 ECL 呼叫端 `0B79`、`0B4A` 與 dispatcher 名字呼叫端取隊伍快照；`0AE5`、`1E42`、`2813` 與 dispatcher `1282` 沒有快照。
6. 句中名的判定不能靠指標：型態 B／D 的字串指標指向堆疊上的整句。可用的訊號是「`_` 槽的文字（去掉兩側空白與句尾標點後）等於隊伍快照的某位隊員名」；語料中名字都是全大寫、前後為空白或標點。
7. 怪物名在範本槽已被 `monsterSlot` 翻譯（ko `테린 우두머리은(는) …` 的名字是韓文，只有助詞標記沒決定）。NPC 名走規格 036 的加註（英文在譯名之後）。
8. 離線重播的 `replay-pages.tsv` 沒有隊伍快照，句中名在其中一律是英文；本規格的驗收要用有隊伍快照的執行期重播，不可只看離線頁面表。

未知：劇情 NPC 入隊、角色死亡後、太空戰鬥的句中名（語料未涵蓋）；`_` 槽含名字以外的字（例如名字前有未知前綴）時的覆蓋率（語料中型態 B 只見三種句型）。

## 3. 契約

範圍只含 ko 與 ja。zh-TW、zh-CN、en、zz 的所有輸出位元組不變（規格 046 §3.1 的凍結範圍）。

### 3.1 助詞標記解析（ko）

純函式 `koResolveMarkers(s string) string`：

- 標記與選擇：`은(는)`→ 前詞有尾音 `은`，無則 `는`；`이(가)`→`이`／`가`；`을(를)`→`을`／`를`；`와(과)`→ 有尾音 `과`，無則 `와`；`(으)로`→ 無尾音或尾音為 ㄹ 用 `로`，其餘 `으로`。
- 前詞的「讀音音節」：標記前一個 rune 若是韓文音節（U+AC00 至 U+D7A3），取它；若是 `)` 且括號內全是 ASCII 字母、數字、`.`、`-`、空白（名字單元的英文加註，規格 038 §3.3），且括號之前緊接韓文音節，取括號前的音節；其餘情形（拉丁字母、數字、標點、字串開頭）**不改**，保留標記。
- 只認標記本身的字串（`koWordMarks` 的括號形）；不碰其他助詞。尾音依 Unicode 的韓文音節分解：`(code - 0xAC00) % 28`，0 為無尾音，8 為 ㄹ。

### 3.2 套用位置

1. **同一次呼叫的組句**：ko 的 `EngineTextCatalog.translateLine` 的結果（`fillTemplateKoJa`、`joinKo` 之後）套 `koResolveMarkers`。涵蓋範本欄位值（怪物名、物品名、§3.3 的玩家名音譯）後接標記的情形。
2. **ECL 頁的跨呼叫**：`EclTextPage` 新增 `lastReading rune`（最後一次畫出的文字的讀音音節，規則同 §3.1；沒有則 0）。續接呼叫（`p != nil && !fresh`）的譯文以標記開頭時，以 `lastReading` 解析前導標記後才排版；
   玩家名呼叫（規格 038 §3.3）的 `lastReading` 取音譯本身（不含加註）的最後音節。只在 ko 版面（`w.layout != nil && w.layout.word`）啟用。
3. 其他路徑（靜態譯文、dispatcher 逐呼叫、選單等）不套用；靜態譯文中的標記由 Python 檢查器（規格 043）管。

### 3.3 句中玩家名（ko、ja）

- 隊伍快照：`observeEclText` 對 `0AE5`、`1E42`、`2813` 取快照，放進 `EclTextEntry.Party`（新欄位）；`NeedsParty` 對 dispatcher `1282` 回 true。這些呼叫端只用快照比對名字，不改變它們原有的判定與計數。
- 名字槽：`EngineTextCatalog` 新增 `TranslateParty(s string, names PartyNames)`（`PartyNames` 為 `func(core string) (reading string, ok bool)`；`Translate(s)` 等於 `TranslateParty(s, nil)`，行為不變）。
  `translateLine` 的 `_` 槽：先照現行試 `monsterSlot`（怪物名優先，現行行為不變）；沒命中且 `names != nil` 時，槽文字去掉兩側空白與句尾 `.,!?` 後若**逐字等於**快照中某隊員名，換成該隊員的音譯（`PlayerNames.Chinese(name, gender)`，lane 自己的語言），保留原有的前後空白與句尾標點（ko 句點、ja `。` 的規則與 `monsterSlot` 相同）。
  不等於任何隊員名者照舊。
- 顯示：只顯示音譯，不加英文註（理由：訊息句由片段組成、版面逐呼叫固定；右欄「窄欄只顯示中文」的決定相同）。音譯超出該句寬度閘門（`stringUnits(zh) > 2*n` 或 ECL 排版失敗）時，整句回到現行的處理（退回原版英文），與其他引擎片段一致。
- 呼叫端接線：ECL 路徑（`0AE5`、`1E42`、`2813`）在 `EclTextWatcher.ObserveEntry` 呼叫 `engine.TranslateParty`，名字解析器由 lane 的 `players` 與 `e.Party` 建；dispatcher 路徑（`1282`）在 `EngineDispatchWatcher.ObserveEntryParty` 的 `default` 分支同樣。`players == nil`（lane 沒有音譯器）時 `names` 為 nil。
- 順序：名字槽換成音譯後，§3.2 第 1 項的標記解析才套用（所以 `플라비우스` 後的 `은(는)` 解成 `는`）。

### 3.4 不變量

1. zh-TW、zh-CN、en、zz 的合成 RGBA 與現行逐位元組相同；機器狀態（記憶體、CPU）不變。
2. ko、ja 在沒有隊伍快照（`names == nil`）時，輸出與現行逐位元組相同（`Translate` 的語意不變）。
3. 變動只出現在：含括號標記且前詞可定音節的 ko 畫面（§3.2），以及句中槽等於隊員名的 ko、ja 畫面（§3.3）。變動集合由測試列出並與預期比對（規格 046 §4 的做法）。
4. 型態 C、E、治療表欄與右欄名字的行為不變。
5. 標記無法解析時（前詞是拉丁字母、數字、標點）保留標記，與現行相同。

## 4. 不在範圍

## 5. 驗收

1. 單元測試：
   - `koResolveMarkers`：五個標記 × 有／無尾音 × ㄹ 尾音（`(으)로`）；括號加註（`설레스트(CELESTE)` 後的標記取 `트`）；前詞為拉丁字母、數字、標點、字串開頭時保留；標記不在字串開頭的位置；與其他助詞（`의`、`에`）相鄰不誤改。
   - `TranslateParty`：名字槽等於隊員名（含前導空白、句尾標點）→ 音譯；不等於→ 英文；怪物名優先；`names == nil` 與 `Translate` 逐字相同；ko 結果的標記已解析；ja 無標記解析。
   - ECL：玩家名呼叫（音譯加註）接標記開頭的續接呼叫 → 標記已解析且排版位置不變；前一呼叫是英文 passthrough 時保留標記；`lastReading` 在清除、換頁後重置。
   - 型態 B（三個呼叫端）與型態 D（`1282`）的合成呼叫：有快照時句中名為音譯，無快照時與現行逐位元組相同；`0B79`／`0B4A` 的既有行為與計數不變。
   - 差分測試：zh-TW、zh-CN、zz 凍結副本（沿用 `layout_freeze_test.go` 的做法）逐位元組不變。
2. 執行期重播（有隊伍快照；從 `cp/*.state` 起跑的執行期，不是離線頁面表）：A（實作 commit 的父 commit）與 B（實作 commit）各自從乾淨匯出建置，ko、ja 各取型態 A、B、D 的時點（證據蒐集的 `plans.txt`、`plans2.txt` 已列出可用的 state 與截止步）：
   記憶體、CPU 雜湊相同；ko、ja 的畫面只在預期矩形內不同；zh-TW、zh-CN、en 的 live RGBA SHA-256 與 A 相同；畫面僅本機檢視，收據只記雜湊與計數。
3. 全套件測試（乾淨匯出）與 `go vet` 通過；`ja_check.sh`、`ko_check.sh` 通過（本規格不改 TSV）。
4. 文件：規格 043、044 §3.8 加指向本規格的 pointer；`docs/re/` 加收據（呼叫端、計數、驗證，不列原版英文句子）；README、CONTEXT、WORKLOG 更新；Issue #39 逐項回報。

## 6. 風險

- 句中名只比對「槽文字逐字等於隊員名」：槽含其他字時不處理（英文保留）；新句型要補證據。
- 玩家把隊員取成與怪物名相同的字串時，怪物名優先（現行行為）；機率低，記為已知。
- 音譯寬度：ko 音譯通常不長於英文，但 ECL 排版失敗時整句退回英文，與現行安全方向一致。
- 同一畫面右欄（只譯名）、ECL 敘事（譯名加註）與訊息句（只譯名）三種寫法並存，是三種版面限制的結果。
- 取隊伍快照增加 `0AE5`、`1E42`、`2813`、`1282` 呼叫的讀取量：每次進入多讀隊伍鏈（約七筆記錄），只在 ko、ja lane 存在時需要。
