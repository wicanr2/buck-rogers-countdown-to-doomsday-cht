狀態：**READY**（2026-09-29，兩輪獨立審查）；§3.4 欄名列修訂 **READY**（2026-09-30，一輪審查，應改已併入）

## 1. 為什麼要做

使用者決定（2026-09-29）：覆繪中的英文與中文字大小要配合。現況每個英數字佔一個原版 8×8 格（2× 為 16 像素寬），
並用原版 8×8 字形放大，英文顯得又大又長（例：「卡頓•特必安(CARLTON TURABIAN)」）。改為半形：字高與中文相同、
寬度一半，兩個半形字佔一個中文字寬。

使用者同日的細部定案：
- 字形用覆繪字型（發行版 Unifont、本機倚天）內的 8×16 半寬 ASCII，不再用原版 8×8 字形。
- 3× 半形字放大 1.5 倍成 12×24，填滿半格。
- 表格最後一欄的數字與座標列也改半形。
- 空白、間隔號 `•`、水平選單項目間的分隔都算半格。

## 2. 證據

- 字型（已證實，Docker 內唯讀掃描本機兩份工作字型）：
  - 倚天 top-pad：ASCII 墨跡 x[4,11]、y[2,14]；`•`（Big5 A145 全形字模）墨跡 x[6,9]、y[6,9]。
  - Unifont 子集：ASCII 墨跡 x[5,11]、y[1,15]；`•` 墨跡 x[5,9]、y[7,11]。
  - 兩份字型都沒有 U+3000 字模；字型編碼器禁止非空白字元的全零字模。
  - 取第 4–11 欄即為完整 8×16 半寬字模，`•` 也在範圍內。
- 3× 垂直對齊（已證實，計算）：倚天半形 12×24 墨跡在格內第 3–22 列，與中文 22×22＋偏移 1 相同；Unifont 半形在
  第 2–23 列，中文在第 1–22 列，差 1 像素。
- 版面（已證實，讀程式）：xlate 以 `X + i*CellW` 定位每個 rune，`CellW=4` 在 2×、3× 為整數像素；一筆 stamp 只有
  一個前景色；改寫判斷（dosgolem 239）在 xlate 內逐筆 stamp 計算；xlate 為多專案共用的通用層。
- 含英數字的覆繪家族（已證實）：ECL 敘事、水平選單、引擎 dispatcher（含座標列、表格、隊伍名）、手札與手札面板、
  劇情第 1／2／6 頁、手冊 2× 與 3×（E1）、手冊英文列、主選單與加入後離開提示（`DOS`，含主選單 3× scoped 路徑）、
  動作列、含 `•` 的怪物名。
- 原版表格列（已證實，規格 029 §2.6 與收據）：最後一欄靠補空白使總長等於原文長度，數字右緣落在原文右緣。
- 動作列現況（強推論，未實跑）：ASCII 助記字母以 `CellW=4` 畫 16×16 字模且位移後超出格寬，可能被裁掉一半。

## 3. 契約

### 3.1 寬度單位與補位

- 半形單位＝4 邏輯像素。半形字元：U+0020–U+007E 與 U+2022（`•`），各 1 單位；其他字元 2 單位。
- 所有容量、換行、欄位計算改以單位計；原本「N 格」的上限換算為「2N 單位」。
- 補位與內容空白分開：
  - 內容中的 U+0020 是 1 單位。
  - 補位先以一個 U+0020 把內容補到偶數單位（對齊原版 8×8 格線），其後以 U+3000 逐格補滿；若補位的終點是奇數單位
    （例如表格最後一欄的起點），在 U+3000 之後再補一個 U+0020。
  - 所有缺字預檢（hmenu、ECL、手札、手冊英文列、選單、加入後提示、說明頁等）把 U+3000 與 U+0020 同樣視為空白，
    不要求字模；`drawGlyphs` 對兩者都只填背景。

### 3.2 半形字模

- 從**未經 031 替換的底字型**（載入的 16×16 GOLEMFNT）衍生半形字型：對每個半形字元取第 4–11 欄、第 0–15 列，
  得 8×16 字模。名稱：底字型名稱加 `.half8x16`；底字型名稱為空時用 `buckrogers.half8x16`。
- 3× 另衍生 12×24：最近鄰放大 1.5 倍（目的 x 取來源 ⌊2x/3⌋、y 取 ⌊2y/3⌋），名稱加 `.half12x24`。
- 字型建置工具（`tools/catalog_font.py`、`tools/eten_font.py`）與執行期衍生時都驗證：每個半形字元的墨跡完全落在
  第 4–11 欄；建置時不符即失敗，執行期不符則半形衍生失敗、該家族照 §3.1 缺字規則處理並記錯誤。
- 中文與其他全形字元的字模、放置、3× 22×22 衍生都不變。規格 031 的原版 8×8 字形不再用於任何覆繪家族。

### 3.3 版面模型

- 遊戲層新增共用函式，把一列文字拆成段：段界＝字寬類別改變或前景色改變。半形段 `CellW=4`、用半形字型；全形段
  `CellW=8`、用原字型。段 X＝列起點＋累積單位×4。
- 2×：半形段 `GlyphScale=1`、`GlyphX=0`、`GlyphY=0`。3×：半形段用 12×24 字型、`GlyphX=0`、`GlyphY=0`。
- 段 key：`<原列 key>#<段序>`，段序自 0 起依由左到右。依賴 key 的檢查（主選單 3× scoped 十鍵白名單、手冊 owner
  的 key 格式）改為先去掉 `#<段序>` 再比對原列 key；各家族 `ActiveKeys` 回傳去重後的原列 key，收據計數不因拆段改變。
- 每 rune 一筆 stamp 的家族（水平選單、dispatcher 經 `HMenuOverlay`、動作列）維持每 rune 一筆與既有 key，只把 X 改為
  累積單位位置；`HMenuRow` 增加每格的單位位置，presenter 與合成讓位使用它，不再用 `len(row.Cells)`。
- 半形字型每個 session 由底字型衍生一次（2× 與 3× 各一個），以同一個指標與 `Name` 傳給所有 presenter
  （`HMenuOverlay`、`EclTextOverlay`、`RuntimeMenuOverlay`、動作列、手札、手冊、劇情頁等）。
- 以 `Frame` 自動定色的家族（選單類、無 style 的手冊）：同一列各段共用整列範圍算出的前景與背景色，不逐段定色。
- **列群組規則**（遊戲層，xlate 不改）：適用以 `Layer.Frame` 格指紋與 239 改寫判斷失效的家族（選單類、動作列、
  無 style 的手冊；加入後選單以 Prewrite 整列 Clear，本規則對它無害但非必要）。同一原列的各段為一個群組，下列任一
  情形發生時，以整列矩形 `Clear` 整個群組：
  1. 任一段被 xlate 移除（`OnDrop` 或段數減少）。
  2. 任一段的任一格變為 `Transparent`（不論來自 `Clear`、`Add`／`Replace` 的部分重疊，或 Frame 指紋失效）。
     檢查點：每次 `Frame` 之後，以及每個 Clear 入口（`RuntimeMenuOverlay.ClearTextCells`、`LiveMenuRuntime.ClearRect`、
     `Replace`／`Add`）呼叫之後，比對群組內各段的 `Transparent`。
  3. 群組任一段本幀出現新的指紋失效錨定格，且群組整體（以原版 8×8 格換算）的有效錨定格 ≤ 2；錨定格由遊戲層在
     Pending 時依段計算。這條補足 239 逐段套用時，段邊界巧合有效格不被判為改寫的漏洞。
  239 本身仍逐段套用（半形段的指紋格為 4×8）。本規則在遊戲層改變 dosgolem 202 §2.3 的部分覆蓋語意：群組任一部分
  失效時整列清除，未被原版覆蓋的部分改為露出原版畫面。
- ECL、水平選單、dispatcher、手札的失效在 watcher 層以整列判斷，列內 stamp 補滿到 8×8 格線，不會殘留半格。

## 5. 驗收
