# 第 25 階段：手冊繁中覆繪倍率決策

## 狀態

完成（使用者決定執行期可切換 2×／3×）

## 本輪目標

以第 17、22、24 階段的真實手冊畫面、2×／3× prototype、整數倍率 renderer 與 runtime
顯示請求為證據，完成手冊繁中段落的產品倍率決策；不在確認前把任何倍率寫成正式規則。

## 已知決策樹

- 父層：手冊段落採 2× 或 3× 整數倍率。
  - 2×：320×200 邏輯畫面輸出為 640×400；每個原版 8×8 格對應 16×16 輸出格，字模填滿格。
  - 3×：輸出為 960×600；每格為 24×24，16×16 字模置中並保留四周 4 px，字體相對較小。
  - 兩案沿用同一個 36×17 邏輯格線，因此每頁容量相同；差異是輸出解析度、字體相對比例
    與視覺密度，而不是頁數。
- 子層：確認倍率後，才能核准 `xlate.Stamp`、正式分頁格線、頁尾提示與同狀態畫面 A/B。

## 範圍

- 回讀第 17 階段 prototype 的程式、metadata 與原生尺寸輸出，不只依賴文字摘要。
- 依 Golden Box／CJK 點陣介面契約，量測安全矩形、實際 glyph footprint、行列容量與裁切。
- 若既有 2×／3× 名稱混用邏輯倍率與預覽倍率，先訂正證據，再向使用者提出單一選擇題。
- 將已確認的決策回填 `CONTEXT.md`、目標規格與 GitHub Issue；未確認前只提交證據與 pending 狀態。

## 不在本輪範圍

- 不在使用者確認前建立 production renderer 或改正常玩家路徑。
- 不決定翻頁按鍵、頁尾文案或其他尚未到前沿的操作細節。
- 不把 prototype 截圖宣稱為玩家可見完成證據。

## 驗收條件

- 2×／3× 比較使用相同原版底圖、相同繁中段落、原生解析度與明確 footprint。
- 提問清楚列出已知事實、實際取捨、Codex 建議與可逆性，且每次只問一個父層決策。
- 使用者選擇後先重述採用／排除方案；確認共同理解後才進入正式 renderer 規格與實作。
- 本輪文件推送 `main` 並更新相關 GitHub Issue。

## 原生 prototype 比較

兩張圖使用同一個 236 字正式段落、同一張 320×200 原版手冊畫面與同一個 36×17 邏輯格線：

| 項目 | 2× | 3× |
| --- | ---: | ---: |
| 實際輸出 | 640×400 | 960×600 |
| 邏輯字格對應 | 16×16 px | 24×24 px |
| 16×16 字模 | 填滿字格 | 置中，四周各 4 px |
| 正式段落 | 7 行／1 頁 | 7 行／1 頁 |
| 708 字壓力樣本 | 20 行／2 頁 | 20 行／2 頁 |
| 安全矩形外變更 | 0 px | 0 px |

- 2× 原生圖：本機被 Git 忽略的 `workplace/phase17/output/actual-2x-page-1.png`
- 3× 原生圖：本機被 Git 忽略的 `workplace/phase17/output/actual-3x-page-1.png`

Golden Box PC-98 對照的穩定模式是 640×400 畫布、約 16×16 CJK cell、寬敘事區約 38 格；
本案 2× 的 640×400、16×16 cell、36 格正文最接近這個閱讀密度。這是跨作品版面參考，
不是《拯救地球》原版行為證據。

Codex 建議選 2×：同頁容量不變，但繁中字模較大、與既有 Golden Box CJK 密度較接近，
也避免用更高輸出解析度換取更小的相對字級。第 22 階段已補齊通用整數倍率 renderer，故
第 17 階段曾有的「2× 需新增底層支援」成本已消失。兩案之後仍可改，但會使畫面收據、
版面規格與玩家偏好驗收重做。

第 32 階段又以真實功能／種族選單 steady 與 Down framebuffer、production `xlate.Draw`、
正式 event／譯文／text-safe rectangles 各重生 2×／3×。兩案幾何皆通過；2× 的中文 ink
填滿 16×16 格，3× 則以 16×16 ink 置中 24×24 格、字間留 8 px。這項第二種 screen type
仍支持 2× 建議，但不替使用者完成決策。詳見
`docs/re/phase-32-menu-overlay-scale-ab-prototype.md`。
