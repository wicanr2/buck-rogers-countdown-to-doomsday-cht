# 第二百九十四階段：原版對 F4（BIOS 字組 3E00h）的使用

日期：2026-09-30
狀態：定稿（主代理審閱，2026-09-30）
用途：規格 040（Issue #35，F4 改為前端保留的語言切換鍵）的原版證據：F4 送進原版時，各畫面有沒有反應。
原始紀錄、腳本與重播輸出只在 ignored `workplace/phase294-f4-usage/`。原版樹 `workplace/original/BRcdoom`
（`GAME.OVR` SHA-256 前綴 `3a4ad4856c08fe59`，`START.EXE` 前綴 `58a34a38b1db4552`），唯讀。

## 結論

- 量到的 14 個畫面（13 個 state）都沒有 F4 專屬行為。所有 trace 裡沒有任何指令拿按鍵值和 `3Eh` 比較，
  集合測試也都判 `3Eh` 不在集合內（已證實，範圍限本次畫面）。
- 除角色頁外，p0（只按 F4）的畫面都和 A 組逐像素相同；p1（再按後續鍵）只有站內選單 `v3` 出現動畫相位差。
  記憶體差異只落在堆疊段 `SS=1841`，外加少數「最後一鍵」一類的變數；F5、F10 對照組跑出同樣的差異（已證實）。
- 角色頁會有看得見的反應：底列選單重建成另一組項目（768 像素不同）。F5、F10 的結果和 F4
  逐位元組相同，所以這是「不認得的延伸鍵」共用的分支，不是 F4 的功能（已證實）。
- 站內選單在 F4 之後再按 Right，站台圖的動畫相位和 A 組不同（475 像素）。F5、F10 同樣如此，
  屬於處理按鍵多花的時間造成的時序位移，不是 F4 的語意（已證實差異與 F5／F10 相同；成因為強推論）。
- 靈敏度正對照：戰鬥移動模式（`x1`）裡 F10 會被 `OVR:0A63C:11E0` 的 `cmp byte [bp-10h],44h`
  接受，畫面差 1,120 像素，F4、F5 則零差（已證實）。所以這個方法看得出單一鍵的專屬反應。
- 對規格 040 的含義：把 F4 改成前端保留，在已量畫面不會拿走任何原版功能。F5–F10 仍照原樣送進原版，
  角色頁的通用反應玩家還是能用其他 F 鍵觸發（強推論，前提是未量畫面也一樣）。

## 方法

- 探針 `tool/main.go`（獨立 module，`replace` 指到 `workplace/dosgolem-clean`，不改該樹），建置成 `f4`
  （SHA-256 前綴 `b373308d14b55d3a`）。dosgolem-clean HEAD `21f750c`，工作樹原本就有 138 個未提交修改
  （`git diff` SHA-256 前綴 `bdabca32a0b339e9`），本次照原狀建置。
- 從 state 載入後依相對步數跑。按鍵只用 `PushBIOSKey` 放進 BDA 環形緩衝，不改其他記憶體，也不存 state。
- 讀鍵紀錄：遊戲程式每次執行 `CD 16` 都記 AH、返回時的 AX／ZF 與 BP 鏈上的呼叫端（含 CodeKey）。
  AH=00 取回的掃描碼是 3Eh 時，從返回點起記逐指令軌跡，直到之後第 8 次空的 AH=01 查鍵（回到閒置輪詢）為止。
- 分組（同一 state、同一 scratch 初始內容、相同步數）：
  - A：不按鍵。B：+2,000,000 步送 F4（`3E:00`）。C：同時點改送 F5（`3F:00`）或 F10（`44:00`）。
  - p0：跑到 +30,000,000 步。p1：另在 +12,000,000 步送後續鍵（下表），跑到 +40,000,000 步。
  - 比較整段 `Mem[0:A0000]`（排除 BDA 鍵盤緩衝 `0041A–0043D`）與 indexed 畫面，另記 CPU、palette 雜湊。
- 決定性：`v9`、`x1`、`v3` 的 A 組重跑一次，記憶體與畫面零差。
- 全部在 Docker：`golang:1.24-bookworm`、`--network none`、`--cpus ≤3`、`--memory 3g`、`--pids-limit 256`、
  目前 UID/GID、原版與來源 state 唯讀。

## 1. 共用讀鍵層（已證實，逐指令軌跡）

| 位址 | 內容 |
|---|---|
| `0C10:02FA` | CRT KeyPressed：`int 16h` AH=01（`0C10:0303`） |
| `0C10:030C` | CRT ReadKey：`int 16h` AH=00（`0C10:031A`）。回 AL=0 時把掃描碼存進 `[DS:95B1]`，下一次呼叫不叫 BIOS，直接回 `3Eh` |
| `09BD:01CE` | 遊戲讀鍵包裝：先 KeyPressed，再 ReadKey，結果放 `[bp-2]`，依序比 `13h`、`15h`、`04h`、`1Ah`、`03h`（控制字元） |
| `OVR:2BA60:1116`–`1146` | 選單輸入：第一次讀到 0 就再讀一次，把 `3Eh` 寫進 `[DS:6B49]`，`[DS:6B1E]=1` 表示延伸鍵 |
| `OVR:2BA60:115D`–`1177` | 水平選單方向鍵：`cmp al,4Bh／4Dh／48h／50h`，F4 都不符，跳 `13F1` 後回呼叫端 |

各畫面在這一層之後由呼叫端再分派（第 2 節）。命名提示不走 `2BA60`，改由 `0763:0845`／`0858` 直接呼叫 ReadKey。
所有 B 組都由 `0C10:031A`（AH=00）取走 `3E00h`，沒有直接讀 BDA 或 IRQ1 的消費者。

補充：

- 「堆疊」指差異全在 `SS=1841` 段，包括已彈出的殘留和仍在使用的框架區域變數。F4 對 F5 的唯一差別是
  某個外層框架裡存的原始鍵值（`3E`／`3F`，例 `SS:3F1A`、`SS:3FCB`、`SS:3F5F`）。p1 的後續鍵多半會把它蓋掉；
  `d28`、`v9` 蓋不到，但之後的畫面與記憶體和 F5 組一致（已證實到 +40M；之後不再讀它為強推論）。
- `DS:6B49` 是選單輸入存的最後一鍵（第 1 節）；`DS:8437`（`gba3`，A=00A0h、B=0140h）用途未知，F5／F10 相同。
- 角色頁的 `[DS:6B1D]`：F4 分支寫入 2，Right 每次加 1（A 組 01→02、B 組 04→05）。用途是選單項目組合或起點，
  屬強推論，未追。
- 命名提示的讀鍵程序與手冊作答輸入同一段（`0763:07E5` 起，見 phase-276）；本次只量命名，沒有開手冊題。

## 3. 未量到的畫面

以下畫面本次沒有 state 或沒有跑，結論不涵蓋：

- 商店（Depot 買賣、物品清單、Trade）、酒吧、診所、港口、訓練與升級確認、隊伍排序。
- 太空航行、星圖、太空戰鬥（飛船介面）。
- 3D 探索的 Area（地圖）、View、Look、Change、Save 等子選單；物品欄（Items）與裝備操作。
- 存讀檔選單本身、標題與片頭、遊戲結束畫面。
- 手冊查詢題畫面（依專案規則不開、不截圖）。
- 按住 F4 自動重複、F4 與 Shift／Ctrl／Alt 組合（`54h`–`71h` 等掃描碼）沒有測。

另有兩個方法本身的限度：

- 逐指令軌跡只記到回到閒置輪詢為止，A/B 窗口最長 38M 步，超過這段時間才出現的延遲反應看不到。
- 「沒有比 3Eh」是就本次執行到的路徑而言。沒走到的分支若用算術或查表判鍵，仍可能對 F4 有反應。

## 4. 重跑

```sh
cd workplace/phase294-f4-usage
NAME=build WD=/workplace/phase294-f4-usage/tool ./run.sh go build -o ../f4 .
NAME=batch CPUS=3 ./run.sh sh batch.sh plan.txt      # A/B（p0、p1），約 2 分鐘
NAME=ctlb  CPUS=3 ./run.sh sh ctlbatch.sh plan.txt   # F5／F10 對照組
./run.sh sh -c 'for f in runs/*-p[01]-B.tsv; do python3 ana.py $f > runs/$(basename $f -B.tsv).ana; done'
./run.sh python3 settest.py runs/v9-p0-B.tsv         # 集合測試的元素與結果
```

- `plan.txt`：每列 `名稱 state scratch種子 後續鍵`。`pair.sh`：單一畫面 A/B、比較、轉 PNG、軌跡摘要。
- `runs/<名稱>-p{0,1}-{A,B}.{tsv,sum,mem,idx,pal,png}`：讀鍵紀錄（`R`／`P`／`Q` 列）、逐指令軌跡（`I` 列）、
  雜湊與傾印；`runs/<名稱>-p{0,1}.cmp` 是差異區段，`.ana` 是比較指令摘要；`runs/ctl-all.txt` 是對照組。
- `f4 cmp PREFIX_A PREFIX_B`：記憶體差異區段（標出堆疊）與 indexed 差異像素數。
- 輸出含原版記憶體與畫面，只留在本機 ignored 目錄。
