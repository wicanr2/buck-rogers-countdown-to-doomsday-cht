# 第十七階段：手冊查詢分頁與倍率對照 prototype

## 結論

由 dosgolem 正常玩家路徑的真實手冊查詢 VRAM 量得金框內部為邏輯座標
`x=7..311、y=7..183`。保留至少一個 8×8 原版字格內距後，prototype 使用 36 欄、
17 行正文，每頁容量 612 個 Unicode 字元。2× 與 3× 都沿用相同原版邏輯格，因此頁數與
容量完全相同；差異落在玩家看到的字級比例與目前 dosgolem 的支援成本。

這一階段只有可丟棄 prototype，沒有 production adapter、正式分頁互動或倍率決策，規格
仍是 DRAFT。

## 目前 renderer 契約與取捨

- 2× 輸出為 640×400，16×16 字模填滿 16×16 輸出格，字體相對畫面較大。
- 3× 輸出為 960×600，16×16 字模置中於 24×24 輸出格，四周各留 4 px；字體相對畫面
  較小，但現有 `xlate.Draw` 已明確支援。
- `xlate.Draw` 現在要求 `scale % 3 == 0`，2× 會直接不畫。採用 2× 必須先把通用 renderer
  的縮放契約改成可驗證的 2×／3× 路徑並補齊測試；採用 3× 不需這項底層變更。
- `xlate.Layout` 的現行契約是一個 Unicode 字元一格，ASCII 也使用完整格。因此英文專名
  字母間距較寬，且可在行尾逐字斷開。這是目前通用 renderer 的限制，不是本 prototype
  自創的差異；若要混合半形排版，須另立資料／API 決策，不在本階段暗改。

## 待使用者決策

根決策是手冊與後續介面採 2× 或 3× 輸出。兩者容量相同；2× 偏向中文閱讀尺寸，但增加
dosgolem 通用 renderer 工作，3× 偏向沿用現有實作與較高輸出解析度，但字體相對較小。
在使用者確認前，兩案都維持 prototype，DRAFT 不升級 READY。
